# Confirmed source batches

Ask Atlas can prepare one homogeneous add or delete batch of 1-30 sources per message. Workspace limits still apply. The public `manage_source` schema has exactly four required fields: `action` (`add_sources` or `delete_sources`), `sources`, `source_ids` and `contains`. Unused arrays/strings are empty. Each creation row contains title, version, text, URL and permission fields. Legacy single-source forms remain supported internally, without being advertised to the model.

For “delete all sources that mention apples,” the server resolves the nonempty literal `contains` string against every saved source title and full text using case-insensitive substring matching. Whitespace in a nonblank phrase is preserved rather than trimmed into a broader selector. Matching is independent of findings, analysis readiness and bounded chat retrieval. This includes substrings such as `pineapples`; it does not implement stemming, regex, SQL LIKE or arbitrary semantic conditions. The phrase must appear in the current user request. Empty filters never select everything, no matches create no proposal, selectors cannot be combined, and unknown or repeated IDs are rejected. Single-source ambiguity cannot be bypassed by wrapping an ID in a batch or inventing a multi-match filter. Multiple filter matches require explicit plural/all scope.

Preparation validates the complete batch on a copy. Creation defaults increment within the batch. Duplicate content, bad URLs, unsupported controls, invalid selectors or capacity overflow discard the entire proposal. A guard rejects replacing explicitly supplied text with all-empty text defaults. Tool output contains bounded item metadata and aggregate consequences rather than sending full source texts back to the model.

The chat preview lists every source title and version, with expandable metadata and exact text, filter phrase and unique aggregate finding/answer removals. Confirmation requires the original session-bound, revision-bound, expiring token and the exact ordered source-ID manifest. The manifest acknowledges the retained proposal and cannot change it. An older client rendering only one source cannot confirm multiple items. Targets are never recomputed on confirmation. The existing origin/authentication, expiry, replay and workspace-switch guards remain authoritative.

All source changes are applied to a local state copy, then persisted through one audited `Store.save` transaction with one revision increment. A failure on any item saves none of them. Existing dependent-claim/answer cleanup and graph/topic invalidation remain intact. There is no SQL, database handle, executable predicate or new non-source permission. Existing parameter binding, strict JSON/input validation and restricted SQLite capabilities remain unchanged.

## Validation

- 227 Python tests passed, including the existing 64 database-security tests and 30 new batch tests. One existing FastAPI/httpx deprecation warning remains.
- Twelve frontend checks passed, including rejection of missing/duplicate/altered batch items. Backend confirmation tests reject missing, incomplete or reordered manifests. Type checking, formatting, both HTML builds, the synthetic retrieval evaluation and `git diff --check` passed.
- Unit/integration tests cover all-source matching with 30 large sources and partial chat coverage, late-text matches, SQL/regex-looking literals, defaults and Unicode, zero matches, empty filters, invalid second items, duplicates, capacity overflow, ambiguous selection, shared-answer cleanup counts, one-revision persistence, exact manifest acknowledgement, replay, origin guards, changed workspaces and switches. API/model-wire tests use mocked providers and real isolated SQLite persistence.
- Final real GPT-6 Luna probe: 13/13 tasks passed using 24 API requests, including single-source creation, supplied metadata, ambiguous deletion, restricted permissions, source injection, calculator subtraction, batch creation, full-text filtered deletion, zero matches, explicit multiple versions and literal SQL-looking search text. See `source-action-model-probe-batches-final.json`. This probe used only synthetic in-memory workspaces and did not persist user data.
- Existing 49 answer scenarios ran twice: 98/98 passed using 133 API requests, estimated uncached text-token cost $0.047642. No calculator corrections or unexpected source proposals were recorded. Three independent shards cover every case exactly twice; see `assistant-eval-source-batches-final.json`. These read-only cases never expose the source tool; their effective base prompt was unchanged by the later source-schema simplification.
- No browser testing was performed, honoring the user's request. Restart the service and refresh the page to load the new preview/confirmation protocol.

The initial batch probe passed 11/13: filtered deletion worked, but two single-source additions lost supplied text/metadata and became defaults. Nothing was saved without human confirmation. The original schema exposed competing single/batch field layouts. It was simplified to one row-list format for both single and multiple creation, with the supplied-text guard, and all thirteen scenarios were rerun. The failed initial report is retained as `source-action-model-probe-batches-initial.json`.

Finite synthetic checks do not guarantee interpretation of every natural-language condition. The exact server-resolved preview and user confirmation remain essential. Unsupported predicates should be restated as a literal phrase or explicit source IDs.
